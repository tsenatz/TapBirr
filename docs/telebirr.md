# Telebirr (Ethio Telecom SuperApp) Gateway Integration

Reference for the Telebirr payment gateway, extracted from the official
[Ethio Telecom developer portal](https://developer.ethiotelecom.et/docs/GettingStarted)
(H5 B2B Web Payment Integration flow) and mapped onto the TapBirr backend.

Implementation:

| File | Purpose |
| :--- | :--- |
| `apps/api/src/telebirr/config.js` | Resolves credentials and endpoints from `.env` |
| `apps/api/src/telebirr/signature.js` | Canonicalisation, RSA signing, callback verification |
| `apps/api/src/telebirr/http.js` | JSON-over-HTTPS transport with a relaxable TLS check |
| `apps/api/src/telebirr/client.js` | Token, create order, query order, checkout URL |
| `scripts/create-order.js` | Standalone sandbox order check |
| `apps/api/tests/telebirr.signature.test.js` | Signing/verification tests (`npm run api:test`) |

---

## 1. Endpoints

| Environment | Base URL |
| :--- | :--- |
| Sandbox (testbed) | `https://developerportal.ethiotelebirr.et:38443/apiaccess/payment/gateway` |
| Production | `https://superapp.ethiomobilemoney.et:38443/apiaccess/payment/gateway` |

| Operation | Endpoint | Method |
| :--- | :--- | :--- |
| Apply fabric token | `/payment/v1/token` | `POST` |
| Create order (pre-order) | `/payment/v1/merchant/preOrder` | `POST` |
| Query order | `/payment/v1/merchant/queryOrder` | `POST` |
| Web checkout (browser redirect) | `https://developerportal.ethiotelebirr.et:38443/payment/web/h5/paygate` | `GET` |

> **Doc inconsistency:** the create-order page documents the checkout host as
> `/payment/web/h5/paygate` while the checkout-URL page uses
> `/payment/web/paygate`. Both are overridable via `TELEBIRR_WEB_BASE_URL`; the
> default here is the `h5` variant, which matches the `WebCheckout` trade type.

## 2. Getting credentials

You **cannot self-serve a testbed key instantly** — the portal hands them out as
part of an organisation onboarding, and four of the five values below are issued
*by Ethio Telecom*, not generated by you.

### 2.1 Register as an organisation

From *In App SDK Integration > Development preparation*:

> If a third-party system wants to access the payment system, the developer must
> register as an organization (merchant or distributor) in the system.

Required (all mandatory): mobile phone number, abbreviation, full name, name and
mobile phone of the organisation contact person, business scope, merchant address.

Two routes:

- **Offline** — email the platform party the required information. On completion
  you receive an email containing the integration details.
- **Online** — register through the Merchant portal; once approved, log in to
  view your information.

Then **subscribe to a payment product** (approved by the MMO) so the
organisation can actually use the selected product.

### 2.2 Receive the platform credentials

After approval the platform sends you four values:

| Value | Goes to `.env` as |
| :--- | :--- |
| Merchant App Id | `TELEBIRR_APP_ID` |
| Merchant Short Code | `TELEBIRR_MERCH_CODE` |
| App Secret | `TELEBIRR_APP_SECRET` |
| Fabric App Id | `TELEBIRR_X_APP_KEY` |

The fabric portal testbed dashboard is <https://developer.ethiotelecom.et/user/dashboard>
("Get Test bed X-APP-Key and appSecret"), linked from every ApplyFabricToken
page. For **production** `X-APP-Key` / `appSecret` there is no self-service —
the docs say to *"contact the ET administrator."*

### 2.3 Generate the RSA key pair (you do this part)

**Two different keys are in play. Mixing them up is the easiest way to break the
integration, so keep them straight:**

| Key | Who owns it | What it does |
| :--- | :--- | :--- |
| **Your** key pair | You | You sign outgoing requests (`preOrder`, `queryOrder`, `token`). **You send your public key to Ethio Telecom** so they can verify them; you keep the private key on your server. |
| **Ethio Telecom's** public key | ET | They use their private key to sign notify callbacks. **They send this to you**, and you use it in `TELEBIRR_PUBLIC_KEY` to verify those callbacks. It cannot be derived from your key pair. |

The docs prescribe generating yours per environment (separate pairs for test and
production):

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private-key.pem
openssl pkey -in private-key.pem -out public-key.pem -pubout
```

Keep the private key safe and do not share it with others. **Send the public key
to the platform** — the gateway verifies every request against it, and will
answer `verify sign failed` until it is registered.

Ethio Telecom also publish an official key generator, `SignTool.zip`
(<https://developer.ethiotelecom.et/developer_tools/static/download/SignTool.zip>),
which produces a key pair in the format their tooling expects and is the safest
choice if you have not yet generated a pair. Registration of the public key
happens through the developer portal (`developer.ethiotelecom.et` → dashboard);
the portal also shows the public key already on file for your account, so check
it there first — if one is already registered, you do not need to upload a new
one. When in doubt, raise it with your ET contact alongside the whitelist request
below; sources describe this as exchanging keys "through the approved channel,"
i.e. the portal or your ET representative rather than email.

### 2.4 Whitelist your URLs

`notify_url` *"must be whitelisted and configured on the SuperApp server in
order to be sent properly"* — callbacks silently do not arrive otherwise. Raise
that with your ET contact at the same time as the key exchange. What ET need in
practice:

- A **publicly reachable HTTPS** URL — plain HTTP is rejected.
- Your **server IP and port 443**, whitelisted on their side.
- Your **public SSL certificate** as a `.crt` file:

  ```bash
  echo | openssl s_client -connect yourdomain:443 -servername yourdomain 2>/dev/null \
    | openssl x509 -out yourdomain.crt
  ```

No public server yet? Two options: point `notify_url` at a tunneller such as
`ngrok` or `cloudflared` (instant public HTTPS domain — handy for a hackathon,
though ET may be reluctant to whitelist a shared tunnel domain), or **skip
callbacks entirely and reconcile with `queryOrder`** on a timer, which needs no
public endpoint at all. Either way the spike itself is unaffected: orders are
created and confirmed with `queryOrder` without a `notify_url`.

## 3. Loading keys into `.env`

`.env` lives at the **repo root** and is already git-ignored. `.env.example`
holds the full annotated template.

```bash
cp .env.example .env
```

Fill in the values you received in §2.2, plus the key pair from §2.3:

```dotenv
TELEBIRR_ENV=sandbox

# Fabric application identity (issued by the fabric portal).
TELEBIRR_X_APP_KEY=your-fabric-app-id
TELEBIRR_APP_SECRET=your-app-secret

# Merchant identity registered against that fabric application.
TELEBIRR_APP_ID=1227484825753601
TELEBIRR_MERCH_CODE=101011

# RSA key pair from §2.3; the public half must be registered with the SP.
TELEBIRR_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----\n"
TELEBIRR_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\nMIIBI...\n-----END PUBLIC KEY-----\n"
```

Notes:

- **PEM newlines.** `.env` cannot contain literal newlines, so paste the key with
  `\n` escapes — `normalizePem()` in `apps/api/src/config/env.js` restores them.
  A base64 body may instead be supplied in `TELEBIRR_PRIVATE_KEY_BASE64` /
  `TELEBIRR_PUBLIC_KEY_BASE64`.
- **Two identity layers.** `X-APP-Key` + `appSecret` identify the *fabric app*;
  `appid` + `merch_code` identify the *merchant*. They are separate values and
  are not interchangeable.
- `TELEBIRR_NOTIFY_URL` must be publicly reachable **and whitelisted** (§2.4).

## 4. Request signing

Every signed request body carries `sign` and `sign_type: "SHA256WithRSA"`.

### 4.1 Canonical string

1. Take every top-level field, **excluding** the keys listed below.
2. Flatten `biz_content`'s members into the same level (`biz_content` itself is
   not signed as an object).
3. **Drop any parameter whose value is empty** — `"If the value of a parameter
   is empty, the parameter is not involved in the signature."`
4. Sort the remaining keys **in ASCII order** (A–Z, then a–z), case-sensitively.
5. Join as `key=value` pairs with `&`. No escaping, no trailing `&`.

Excluded fields:

```
sign  sign_type  header  refund_info  openType  raw_request
wallet_reference_data  biz_content
```

> The Interface Signing rules only name `sign`, `sign_type`, `biz_content` and
> null parameters. The extra five come from the official tooling samples, which
> gateways of this family all share. We use the **union** — dropping an excluded
> field costs nothing, but signing one that the gateway skips yields a
> mismatched canonical string.

Implemented by `signature.canonicalize()`. Both canonical strings published in
the portal reproduce byte-for-byte, and are pinned as tests.

From the RequestSignatureProcess sample:

```
appid=1227484825753601&merch_code=101011&merch_order_id=1755866910890&method=payment.preorder&nonce_str=H5QN4M6EAB2TXXVFK8SVV0RW6UFASICS&notify_url=https://www.google.com&timeout_express=120m&timestamp=1755866911&title=diamond_1.5&total_amount=1.5&trade_type=Checkout&trans_currency=ETB&version=1.0
```

From the Development preparation rawRequest example:

```
appid=1072905731584000&business_type=BuyGoods&merch_code=200001&merch_order_id=201907161732001&method=payment.preorder&nonce_str=fcab0d2949e64a69a212aa83eab6ee1d&notify_url=http://test.payment.com/notify&redirect_url=http://test.payment.com/redirect&timeout_express=120m&timestamp=1535166225&title=iphone1&total_amount=12&trade_type=Checkout&trans_currency=ETB&version=1.0
```

### 4.2 Signature

Sign that UTF-8 string with the RSA private key and base64-encode the result.
`signature.withSignature()` returns a copy of the payload with `sign` and
`sign_type` attached.

#### Signature padding {#signature-padding}

The portal's authoritative **Interface Signing** rules (In App SDK >
Development preparation) state:

> - Signature algorithm: SHA256withRSA
> - Fill mode: **PSS**
> - Parameters not involved in the signature: null parameters, `sign`,
>   `sign_type`, and `biz_content`

So the default is PSS (RSASSA-PSS, SHA-256 + MGF1-SHA-256):

| `TELEBIRR_SIGN_PADDING` | Algorithm | Used by |
| :--- | :--- | :--- |
| `pss` *(default)* | RSASSA-PSS, SHA-256 + MGF1-SHA-256 | Spec, Node.js (`SHA256withRSAandMGF1`), C# (`RSASignaturePadding.Pss`) |
| `pkcs1` | RSASSA-PKCS1-v1_5 | Python (`PKCS1_v1_5`), PHP (`Crypt_RSA`) |

The Python and PHP demos contradict the spec; `sign_type` stays
`"SHA256WithRSA"` either way, so it gives no hint as to the padding. **If the
gateway answers `verify sign failed`, flip this first**, then check that your
canonical string matches §4.1 exactly. Both modes are covered by tests.

### 4.3 Timestamp and nonce

- `timestamp` — Unix time **in seconds** (10 digits). The docs label the field
  `string(13)` but every sample is 10 digits and says "the unit is second"; a
  millisecond value is rejected.
- `nonce_str` — 32 characters. Uppercase hex matches the docs' samples.

## 5. Sandbox flow

```
applyFabricToken  →  requestCreateOrder  →  build checkout URL
                                              ↓ (payer pays in browser)
                                        POST notify_url callback
                                              ↓ (or missed callback)
                                           queryOrder
```

### Step 1 — Apply fabric token

```http
POST /apiaccess/payment/gateway/payment/v1/token
Content-Type: application/json
X-APP-Key: <TELEBIRR_X_APP_KEY>

{ "appSecret": "<TELEBIRR_APP_SECRET>" }
```

Response:

```json
{
  "effectiveDate": "20221101132422",
  "expirationDate": "20221101142422",
  "token": "Bearer 94cc42be4412696d754508c06ca1db20"
}
```

The token is cached in-process until 60 s before `expirationDate`
(`yyyyMMddHHmmss`, UTC) and reused as the `Authorization` header. Note the
`Bearer ` prefix is already part of the returned value — do not add another one.

### Step 2 — Create order

```http
POST /apiaccess/payment/gateway/payment/v1/merchant/preOrder
Content-Type: application/json
X-APP-Key: <TELEBIRR_X_APP_KEY>
Authorization: Bearer 94cc42be4412696d754508c06ca1db20
```

```json
{
  "method": "payment.preorder",
  "version": "1.0",
  "timestamp": "1535166225",
  "nonce_str": "fcab0d2949e64a69a212aa83eab6ee1d",
  "biz_content": {
    "appid": "1072905731584000",
    "merch_code": "000000",
    "merch_order_id": "201907161732001",
    "title": "iphone1",
    "total_amount": "12",
    "trans_currency": "ETB",
    "timeout_express": "120m",
    "business_type": "TransferToOtherOrg",
    "trade_type": "WebCheckout",
    "notify_url": "http://test.payment.com/notify",
    "redirect_url": "http://test.payment.com/redirect"
  },
  "sign": "JYyVqFAmdgBG4n1eBQYUwNlC...",
  "sign_type": "SHA256WithRSA"
}
```

`biz_content` fields:

| Field | Type | Req | Notes |
| :--- | :--- | :--- | :--- |
| `appid` | `String(32)` | yes | Merchant app id |
| `merch_code` | `String(16)` | yes | Merchant code |
| `merch_order_id` | `String(64)` | yes | Your idempotency key |
| `title` | `String(512)` | yes | Order title |
| `total_amount` | `String(20)` | yes | Decimal string, e.g. `"12"` |
| `trans_currency` | `String(3)` | yes | `ETB` |
| `timeout_express` | `String(10)` | yes | e.g. `120m` |
| `business_type` | `String(32)` | yes | e.g. `TransferToOtherOrg` |
| `trade_type` | `string` | yes | `WebCheckout` for browser redirect |
| `notify_url` | `String(512)` | yes | Must be whitelisted on the SP |
| `redirect_url` | `String(512)` | no | Where the payer lands after paying |
| `callback_info` | `String` | no | Echoed back on the callback |
| `payee_type` | `String` | no | `3000` = Organization Operator |
| `payee_identifier` | `String` | no | Merchant code or short code |
| `payee_identifier_type` | `String` | no | `04` = receive via short code |

`trade_type` options: `InApp`, `Cross-App`, `WebCheckout`, `PWA`, `QrCode`,
`QuickPay`, `BankTrade`.

### Step 3 — Response format

```json
{
  "result": "SUCCESS",
  "code": "0",
  "msg": "success",
  "nonce_str": "97fe4ae0c0604854a749fbf2cc1cc712",
  "sign": "Eo4Bvwx9rpaWAO+iYzaaXHoWBWbYcCGnVZMEcG5TPb8w...",
  "sign_type": "SHA256WithRSA",
  "biz_content": {
    "merch_order_id": "1705460512562",
    "prepay_id": "080075a4e3213924de2b3b84ad3cac0a6a6001"
  }
}
```

| Field | Type | Notes |
| :--- | :--- | :--- |
| `result` | `String` | `SUCCESS` or `FAIL` |
| `code` | `String` | `0` = success, otherwise a business error code |
| `msg` | `String` | Human-readable description |
| `sign` | `String(512)` | Signature over the response body |
| `sign_type` | `String` | `SHA256WithRSA` |
| `biz_content.merch_order_id` | `String(64)` | Echoed order id |
| `biz_content.prepay_id` | `String(128)` | Handle for the checkout URL |

**Two distinct error envelopes**, both arriving with HTTP `200` — see §6.

### Step 4 — Build the checkout URL

`prepay_id` is exchanged for a browser URL by signing a second, *flat* payload
and appending it as a query string:

```
webBaseUrl
  ?appid=<appid>&merch_code=<merch_code>&nonce_str=<nonce>&prepay_id=<prepay_id>&timestamp=<ts>
  &sign=<urlencoded base64 sign>&sign_type=SHA256WithRSA
  &version=1.0&trade_type=WebCheckout
```

`createCheckoutUrl()` handles this. The payer enters their short code,
operator ID and PIN on the Telebirr checkout page; on success they are
redirected to `redirect_url`.

### Step 5 — Callback payload (notify)

The gateway `POST`s a **flat** body (no `biz_content`) to `notify_url` once
payment completes:

```json
{
  "notify_url": "http://197.156.68.29:5050/v2/api/order-v2/mini/payment",
  "appid": "853694808089634",
  "notify_time": "1670575472482",
  "merch_code": "245445",
  "merch_order_id": "1670575560882",
  "payment_order_id": "00801104C911443200001002",
  "total_amount": "10.00",
  "trans_id": "49485948475845",
  "trans_currency": "ETB",
  "trade_status": "Completed",
  "trans_end_time": "1670575472000",
  "sign": "AOwWQF0QDg0jzzs5otLYOunoR65GGgC3hyr+oYn8mm1Qph6Een7C...",
  "sign_type": "SHA256WithRSA"
}
```

| Field | Type | Req | Notes |
| :--- | :--- | :--- | :--- |
| `merch_order_id` | `String(64)` | yes | Your order id |
| `payment_order_id` | `String(64)` | yes | Gateway transaction id |
| `trade_status` | `String(4)` | yes | See below |
| `trans_end_time` | `String` | yes | Milliseconds since epoch |
| `sign` | `String(512)` | yes | Signature over the callback body |
| `sign_type` | `String` | yes | `SHA256WithRSA` |
| `appid` | `String(32)` | no | Merchant app id |
| `merch_code` | `String(16)` | no | Merchant code |
| `notify_time` | `string` | no | Milliseconds since epoch, UTC |
| `total_amount` | `String(20)` | no | Decimal string |
| `trans_currency` | `String(3)` | no | `ETB` |
| `trans_id` | — | no | Present in the sample; undocumented in the table |
| `callback_info` | `String` | no | Echoed from the create-order request |
| `notify_url` | `String(512)` | no | Echoed back |

`trade_status` values:

| Value | Meaning |
| :--- | :--- |
| `Paying` | User has paid |
| `Pending` | Payment completed, awaiting order sync |
| `Completed` | **Payment completed — treat as success** |
| `Expired` | Status unclear after reconciliation |
| `Failure` | Payment failed |

Verify with `verifyCallback(body, config)`. The callback is canonicalised and
verified exactly like a request, but with the **SP's public key** (not yours),
and no `biz_content` to flatten. Always verify before crediting an order, and
treat `Completed` as the only success terminal state.

### Step 6 — Query order (reconciliation)

```http
POST /apiaccess/payment/gateway/payment/v1/merchant/queryOrder
```

Same headers as create order; body uses `method: "payment.queryorder"` with
`biz_content` containing `appid`, `merch_code` and `merch_order_id`. Use it when
a callback never arrives — call it on a timer for orders still `Pending`, and
never trust browser redirect as proof of payment.

Response (verified against the sandbox — note the field is `order_status`, **not**
the `trade_status` used by callbacks, and the status vocabulary differs too):

```json
{
  "result": "SUCCESS",
  "code": "0",
  "msg": "success",
  "nonce_str": "7164aec172224168952e08895f619b11",
  "sign": "ZP85Kmz+...==",
  "sign_type": "SHA256WithRSA",
  "biz_content": {
    "merch_order_id": "415df60fc901a8ba",
    "order_status": "WAIT_PAY",
    "trans_currency": "ETB",
    "total_amount": "10.00",
    "trans_id": ""
  }
}
```

| Field | Notes |
| :--- | :--- |
| `biz_content.order_status` | e.g. `WAIT_PAY`. Empty `trans_id` means unpaid. |
| `biz_content.trans_id` | Gateway transaction id; `""` until paid |
| `biz_content.total_amount` | Decimal string, two places (`"10.00"`) |

So there are **three status vocabularies** in play: `order_status` here,
`trade_status` on callbacks, and whatever the checkout page shows. Do not
compare them directly — map them yourself, and treat a non-empty `trans_id` or
`SUCCESS`-equivalent as the only trustworthy signal that money moved.

## 6. Error handling

The gateway returns **HTTP 200 for most failures**, with one of two envelopes.
`unwrap()` in `client.js` normalises both into a `TelebirrError`.

**Fabric-layer rejection** — bad/expired `X-APP-Key` or `appSecret`:

```json
{
  "errorCode": "49401031101",
  "errorMsg": "The operation is restricted and the access function is not authorized.Detail:Forbidden !  err:App key or app secret is invalid!",
  "errorSolution": "1. Check whether the authentication token or Basic authentication information is correctly set in the interface. ..."
}
```

**Application-layer rejection** — `result: "FAIL"` with a business code:

```json
{ "result": "FAIL", "code": "<business code>", "msg": "...", ... }
```

Success is `result == "SUCCESS"` **and** `code == "0"`.

## 7. TLS on the sandbox

The sandbox certificate is a legitimate GlobalSign EV cert for
`developerportal.ethiotelebirr.et`, but the **issuing intermediate is missing
from most system trust stores**, so verification fails with:

```
SSL certificate problem: unable to get local issuer certificate
```

Hence `TELEBIRR_TLS_INSECURE=true` by default (matching the official demos,
which all set `rejectUnauthorized: false`). The hostname still has to match.

**Set `TELEBIRR_TLS_INSECURE=false` in production.** To keep verification on in
the sandbox instead, supply the intermediate:

```bash
export NODE_EXTRA_CA_CERTS=/path/to/GlobalSign_GCC_R3_EV_TLS_CA_2025.crt
```

## 9. Mapping onto the TapBirr contract

`docs/API.md` §4 defines an abstract contract. The gateway fills it in as:

| TapBirr contract | Telebirr |
| :--- | :--- |
| `POST /api/payments/initiate` | `applyFabricToken` + `preOrder` + checkout URL |
| `checkoutUrl` | `createCheckoutUrl(prepay_id)` |
| `transactionId` | `merch_order_id` (yours) |
| `gatewayReference` | `payment_order_id` / `trans_id` |
| `status` | `trade_status`, `Completed` = `SUCCESS` |
| `amount` / `currency` | `total_amount` (decimal string) / `trans_currency` |
| `POST /api/payments/callback` | gateway notify; **verify `sign` first** |
| `GET /api/payments/:id/status` | `queryOrder` |

Differences worth honouring in the backend:

- **Amounts are decimal strings** on the wire, not numbers.
- **The callback is the only trustworthy completion signal.** The redirect to
  `redirect_url` is user-controlled and proves nothing.
- **Callbacks can be lost.** Reconcile with `queryOrder` rather than relying on
  a single delivery.
- **Sign verification is mandatory** on the callback — the body includes an
  amount, and an unverified webhook is trivially forged.

## 10. Known doc gaps

Recorded so they are not mistaken for bugs in this implementation:

- `timestamp` is typed `string(13)` but specified and sampled in seconds (10).
- Padding for `SHA256WithRSA` disagrees with itself: the Interface Signing rules
  say PSS, but the Python and PHP demos use PKCS#1 v1_5 (§4.2). The spec
  wording is treated as authoritative.
- The Python and PHP samples sort the canonical string and then join **only the
  values**, dropping the `key=` prefixes — that contradicts the Node.js, Java and
  C# samples and would not verify. §4.1 follows the majority (correct) behaviour.
- The Python and PHP samples also omit the documented **empty-value exclusion**
  rule, and do not skip `biz_content` as a whole.
- Checkout base path differs between the create-order and checkout-URL pages (§1).
- `trans_id` appears in the callback sample but not in its parameter table.
- Production credentials require contacting the ET administrator; there is no
  self-service production key.
